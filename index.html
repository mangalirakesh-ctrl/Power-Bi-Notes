01Business Intelligence (BI) Concepts

Business Intelligence turns raw data into insights that support business decisions. It covers data collection, integration, storage, analysis, visualization and reporting.

Evolution of BI

1960s–1980sManual reporting: static reports built by IT.
1990sData warehousing: centralized, structured history.
2000sWeb-based BI: reports and dashboards in the browser.
2010s–presentSelf-service, AI/ML and cloud BI.

Four types of analytics (with examples from our sample data)

1. Descriptive: what happened?“Total sales were 19,025; West was the top region at 6,200.”
2. Diagnostic: why?“February jumped 47% vs January because West bought 7 laptops (5,600).”
3. Predictive: what might happen?“Forecast next month's sales from the monthly trend.”
4. Prescriptive: what should we do?“Stock more laptops for the West region.”

BI architecture: five layers

1 · Data sourcesExcel, CSV, databases, ERP/CRM, web services, cloud apps
▼
2 · ETL (Extract, Transform, Load)Cleaning, shaping and combining data. In Power BI this is Power Query
▼
3 · Data storageData warehouse, data marts, or the Power BI in-memory model
▼
4 · Analytics / OLAP modelsRelationships, measures and calculations (DAX)
▼
5 · Presentation toolsReports, dashboards and apps people actually use

Power Query in action

A cleanup recipe recorded as steps

let
    Source   = Csv.Document(File.Contents("C:\Data\FactSales.csv"), [Delimiter=","]),
    Headers  = Table.PromoteHeaders(Source, [PromoteAllRows=true]),
    Typed    = Table.TransformColumnTypes(Headers, {{"SalesAmount", type number}, {"Date", type date}}),
    Filtered = Table.SelectRows(Typed, each [SalesAmount] > 0)
in
    Filtered

Each line appears in the Applied Steps pane (Source → Promoted Headers → Changed Type → Filtered Rows). Refresh replays them on new data.

Relationships (Model view)

CardinalityMeaningExample
One-to-many (1:*)One row in the “one” table matches many rows in the “many” tableOne product → many sales rows. The most common and recommended type
Many-to-one (*:1)Same as above, viewed from the other sideFactSales → DimProduct
One-to-one (1:1)Each row matches at most one rowCustomer ↔ Customer Profile; consider merging into one table
Many-to-many (*:*)Both sides have repeated valuesUse sparingly; a bridge table is usually cleaner

Cross-filter direction: Single (dimension filters fact, the default and best for performance) or Both (filters flow either way; use carefully). Only one relationship between two tables can be active; extra ones are inactive and activated inside a measure with USERELATIONSHIP().

06Data Modeling

A good model improves accuracy, performance, flexibility, scalability and maintainability. The recommended design is the star schema: one central fact table surrounded by dimension tables.

Star schema (recommended)

Fact tableNumbers you measure (Qty, SalesAmount, Cost) plus keys. Many rows, narrow.
Dimension tablesDescriptive attributes you slice by (Product, Customer, Date). Fewer rows, wide.
Why it's bestSimple, fast, and DAX filter propagation works predictably.

Snowflake schema

A snowflake normalizes dimensions into sub-tables. It reduces redundancy but adds joins and complexity and can slow queries. Prefer a star schema; flatten (merge) lookup tables like Category into the dimension when you can.

Flattening a snowflake into a star

In Power Query, merge DimCategory into DimProduct (Home → Merge Queries), expand the Category column, then remove the extra table. The model goes from 3 hops to 1.

Date table

Always use a dedicated calendar table, related to the fact table's date column, and mark it as a date table (Table tools → Mark as date table). Time-intelligence functions need it.

Modeling best practices

  • Use star schema with one-to-many, single-direction relationships.
  • Use integer surrogate keys for relationships when possible.
  • Hide key columns and fact columns that users should not drag directly.
  • Avoid bi-directional and many-to-many relationships unless required.
  • Remove unused columns before loading to shrink the model.

07DAX (Data Analysis Expressions)

DAX is the formula language for measures, calculated columns and calculated tables. Every result below is computed from the sample data. Click a code block to copy it.

Your first measures

Total Sales = SUM(FactSales[SalesAmount])
Total Cost  = SUM(FactSales[Cost])
Profit      = [Total Sales] - [Total Cost]
Profit Margin % = DIVIDE([Profit], [Total Sales])
Orders = COUNTROWS(FactSales)
Customers = DISTINCTCOUNT(FactSales[CustomerKey])
MeasureResultHow
Total Sales19,025Sum of all SalesAmount values
Total Cost14,100Sum of Cost
Profit4,92519,025 − 14,100
Profit Margin %25.9%4,925 ÷ 19,025. DIVIDE avoids divide-by-zero errors
Orders8Rows in FactSales
Customers4Distinct customer keys

Unit Price = DIVIDE(FactSales[SalesAmount], FactSales[Qty])   // calculated column

Filter context

A measure's result depends on the filters around it: rows, columns, slicers and filters of the visual. Same measure, different answer in every cell:

Total Sales in a matrix (Region × Category)

The highlighted cell is evaluated with filter context Region = West and Category = Electronics, so only West electronics rows are summed: 5,600. The totals row/column simply remove one of the filters.

CALCULATE: change the filter context

Electronics Sales = CALCULATE([Total Sales], DimProduct[Category] = "Electronics")
East Sales        = CALCULATE([Total Sales], DimCustomer[Region] = "East")
Sales % of Total  = DIVIDE([Total Sales], CALCULATE([Total Sales], ALL(DimCustomer)))

Electronics Sales = 16,400 (laptops 12,000 + monitors 4,400)
East Sales = 5,125
ALL(DimCustomer) removes the region filter inside CALCULATE, so each region's sales is divided by the grand total of 19,025.

Row context, iterators and context transition

Row context“The current row.” Exists in calculated columns and iterator functions. FactSales[SalesAmount] / FactSales[Qty] works because each row is evaluated one by one.
Iterators (X functions)SUMX, AVERAGEX, MAXX, COUNTX: evaluate an expression per row, then aggregate.
Context transitionWhen CALCULATE (or a measure reference) runs inside row context, the current row becomes a filter.
Profit (iterator) = SUMX(FactSales, FactSales[SalesAmount] - FactSales[Cost])
Avg Sales per Customer = AVERAGEX(DimCustomer, [Total Sales])
Customer Sales = [Total Sales]     // calculated column in DimCustomer → context transition

Context transition: a measure used inside a calculated column

For each customer row, [Total Sales] automatically filters FactSales to that customer. Average per customer: (5,125 + 6,200 + 2,660 + 5,040) ÷ 4 = 4,756.25. The iterator Profit = 4,925, identical to SUM − SUM.

Ranking

Customer Rank = RANKX(ALL(DimCustomer[Customer]), [Total Sales])

Time intelligence

First create and mark a calendar table:

DimDate = CALENDAR(DATE(2024, 1, 1), DATE(2024, 12, 31))
Month   = FORMAT(DimDate[Date], "MMM")      // calculated column
Sales YTD    = TOTALYTD([Total Sales], DimDate[Date])
Sales LM     = CALCULATE([Total Sales], DATEADD(DimDate[Date], -1, MONTH))
Sales MoM %  = DIVIDE([Total Sales] - [Sales LM], [Sales LM])
Sales LY     = CALCULATE([Total Sales], SAMEPERIODLASTYEAR(DimDate[Date]))

Monthly results

Feb MoM = (9,365 − 6,360) ÷ 6,360 = 47.2%. YTD is a running total within the year. Sales LY is blank because the sample has no 2023 data.

11Best Practices

Modeling

  • Use a star schema; one-to-many, single-direction relationships.
  • Prefer measures over calculated columns where possible (no storage cost, reacts to filters).
  • Use a marked date table.
  • Do transformations in Power Query (close to the source), calculations in DAX.

Report design

  • Limit the number of visuals per page (a handful of key visuals loads faster and reads better).
  • Put the most important numbers top-left; use consistent colors and fonts.
  • Use slicers and drill-through for detail instead of crowding the page.
  • Hide unnecessary columns and fields from Report view.

Performance checklist

✅ Remove unused columnsSmaller model, faster refresh.
✅ Right data typesNumbers as numbers, dates as dates; avoid high-cardinality text columns.
✅ Use Performance AnalyzerView → Performance Analyzer to see which visual or DAX query is slow.
✅ Use incremental refreshFor large, growing tables.
✅ Avoid bi-directional filtersUnless there's a clear need.
✅ DocumentAdd descriptions to measures and tables for your team.
